# Research Rigor

Accuracy matters more than speed. These apply to any investigation — research, debugging, or answering a factual question.

- Always web-search for cost/pricing data, niche technical claims, and API behavior. Do not rely on training data for these.
- Include footnote references to pricing docs and technical sources. If you don't have a link, don't infer.
- Clearly label all inference or unsubstantiated claims.
- Take your time. Think deeply before answering.
- **Exhaust before accepting.** If a search returns paginated results, follow every page. If a query returns exactly the max result count, assume truncation and narrow the query. Never stop at the first page.
- **Don't silently degrade.** If you can't get the exact data requested, don't substitute a weaker version without flagging it. Say what you tried, what you got instead, and why it's less complete. Ask the user before moving on with partial results.
- **Try at least 3 approaches before reporting a gap.** Wrong username, empty results, unexpected format — these mean the method failed, not that the data doesn't exist. Try alternative queries, different search patterns, different APIs. Only escalate to the user when you've genuinely run out of ideas.
- **Permission denied = hard stop.** If any tool returns a permission/authorization error, stop immediately. Do not retry, do not try to work around it, do not continue with other agents. Report the exact error to the user and wait for instructions. This is a security boundary, not a search problem.
- **Two greps agreeing is not corroboration if they share a pattern.** Never report a count from `grep -c` alone. A character class silently drops non-matching members: `[A-Z_]+` and `[a-zA-Z]+` both skipped `IS_BASE64_ENCODED_DATA` because of the digits, and agreed on a wrong total. The same class dropped `AWS_ENDPOINT_URL_S3` from a config sort and moved it to the wrong place. Extract and enumerate the actual matches, then count those.
- **A line-based pattern lies in both directions once the file has states.** A `#` inside a fenced code block is not a heading, and a check for "headings missing a blank line" reported two hits in files that had none, because the pattern cannot see the fence. Every empty-result trap here has a mirror image: a finding can be an artifact of the instrument exactly as easily as a zero can, and it arrives looking like work product rather than like a bug. Make the checker track whatever state it depends on (fence, quote, comment), and have it print how many real instances it examined, so a clean result is evidence it looked rather than evidence of nothing.
- **"I could not verify this, you decide" is a claim about the checker's reach, not about the evidence.** A code review surfaced two contradictory figures for one measurement and declined to choose, on the grounds that picking either would be a guess. The provenance record settled it in two commands: the figure it would have had to guess at had been written down all along, in a file outside what a delegated agent could see. Before accepting an escalation, go looking for the run log, notebook, or provenance file that produced the number.
- **An empty search result is a claim about the index, not about reality.** Before concluding something doesn't exist, confirm the source is actually indexed and in scope. Archived repositories, for instance, are often excluded from code search.
- **A command that never ran returns nothing, which looks exactly like a result of nothing.** In zsh a failed glob aborts the whole command, so `grep -rn X --include=*.md .` and `grep X *.json *.csv` (when no `.csv` exists) print a "no matches found" line and never execute the grep at all. That happened three times in one session, once concluding all 8 of 8 contract ids were absent from a file that held 4 of them. Quote glob-looking arguments, and when a search over N things returns 0 for all N, suspect the command before the world.
- **When you claim a set is complete, check whether the argument rests on an unverified property of the tool.** The trap is not a wrong number, it is a sound-sounding argument resting on an assumed guarantee, with nothing about the output looking off. NRDB's `FACET … LIMIT MAX` returns 5,000 facets that are *not* the largest, so "the smallest value returned is far below my threshold, therefore everything above the threshold is present" proved nothing about a 2,924-account population. Re-verify by a method that cannot share the assumption: partition the space into pieces small enough that no limit binds, treat any piece that comes back exactly at the limit as unusable rather than as data, then diff against the original answer and account for every difference instead of noting that the totals look close.
- **A decomposition that multiplies out exactly still proves nothing about its endpoints.** Explaining a gap by stacking filters is only as good as the measurement at each end, and the arithmetic closing to the last digit feels like the verification when it is only internal consistency. Real case: two figures for one quantity differed 5.334x, and I attributed that to three nested filters whose factors multiplied to 5.3337 against an observed 5.3337. The chain was wrong. One endpoint had never been measured, only assumed to be the narrowest filter's value; the other side's number was that filter plus a separate 4.5x defect, and the true factor for the step I named was 6.9x, not the 1.53x the chain needed. Measure both endpoints with their own query before decomposing, and pull the finest grain both sides can produce, a daily series rather than a total, so per-unit agreement is something you observe instead of infer from one ratio.
- **A grouped breakdown is not a partition until you add it up.** Group-by results routinely omit rows whose grouping key is null, with no marker in the output that anything is missing, so the categories look exhaustive and every individual figure is correct. Two shares computed from one such breakdown then get compared against a total that includes rows neither share contains. Real case: an NRQL `FACET` over a query-capability attribute dropped 216 billion of 275 trillion scanned events, and only summing the facets against the unfaceted total revealed it, whereupon the missing bucket turned out to have a named counterpart in the other data source. Sum the parts against the independently-measured whole before quoting any share, and when they disagree, find the residual instead of noting that it is small.
- **A search that comes back empty or surprisingly thin gets a positive control before you believe it.** Re-run the same query against a case you already know matches. If the control also comes back empty, the instrument is broken and the result says nothing about the world. Three real misses: `grep -E 'class Foo\|module Foo'` reported four classes missing that all existed, because `-E` reads `\|` as a literal pipe; `'^| `'` reported eight table rows missing because the names sat in column two; NRDB `keyset()` reported an overflow blob missing because `keyset()` does not list blob attributes at all, and the blob turned out to be there in full under `blob()`. That last shape is the dangerous one, because the pattern is fine and the instrument simply does not surface that kind of thing, so no amount of re-reading the pattern finds the bug. When the question is "does X exist," prefer the direct read: load the file, run the thing, or query the attribute by name alongside a control that must return a hit.
- **A control drawn from the same subset as your search validates the pattern, not the scope.** Pick the control so it differs along the axis you could be blind to. Twice in one session I concluded a NR cell was decommissioned: the cell lived under the Azure paths and I had searched only the AWS ones, and my control cell was *also* AWS, so it passed and confirmed nothing. Then the same shape again with a grep pattern that had already failed on the control case and was never re-run against the target after I fixed it. Before believing an absence, ask "what dimension does my control share with my search" — cloud, region, directory, event type, account — and re-control across it.
- **An output limiter decides what you conclude, and it fabricates absences that look like findings.** The empty-result traps above are about false negatives; this is the mirror, and it arrives as a confident discovery rather than a zero. `grep -rn X . | grep -v node_modules | head -5` returned five hits, all under `.claude/worktrees/`, so I reported that a repo's public-GitHub metadata existed "only inside a worktree" and called it significant. The main-tree hits that disproved it were real and were sitting at position six, pushed there by nothing but path sort order. Re-running without `head` showed them immediately. A limiter is a sampling decision, so never let `head`, `-m`, `LIMIT`, or a result cap stand between a search and a conclusion about what does not exist: count the matches first (`grep -c`, or pipe to `wc -l`), then look at a sample if the count is large. Sorting hits so the paths you care about come first is not a fix, it is the same bug with better luck.
- **A warning is a claim, and it gets the same verification as any other.** Telling the user their own change looks wrong asks them to undo correct work, so the bar is a check, not an inference. I flagged a deleted `.gitignore` entry as newly exposing a private directory, without once looking for the directory: it had been moved outside the repo that same day, and my own notes already said so. Before flagging, run the one command that settles it, and re-read what you already know. A false alarm also spends the credit the next real one needs.
- **Before handing the user a query to run, confirm the target data exists and send the fewest queries that decide the question.** Check the metric or event is emitting first. A pack of queries against a dormant source wastes their time and looks like progress. Two decisive queries beat nine speculative ones.
- **For "does this API/platform support X" questions, verify by introspection or a live call, not web search.** A GraphQL schema answers definitively (`{ __schema { mutationType { fields { name } } } }`) in one call; web-search-grounded answers gave a wrong REST host, a wrong auth header, and a fabricated syntax example (`FROM AccountA` — not real NRQL) in one session, each stated with the same confidence as the true ones. An internal SME's answer (a colleague, a runbook) beats both when available — it caught a wrong default (`GatewayQuery`) that every prior verification step had missed because nothing was actually wrong with the query, just the choice of event type.
- **Pre-register the success criteria, then reconcile every unit of the difference before calling a result pass or fail.** A criterion that fails can mean the change did *more* than you modeled rather than less, and enumerating the set difference is the only way to tell. Real case: I predicted a Terraform plan's destroy and add counts would be unchanged apart from three replacements disappearing. They dropped further than that, which read as an unexplained side effect until the before/after diff of resource actions showed 18 removed and 3 added, each attributable: 9 data sources that now resolve at plan, a 4th replacement downstream of one of them, 5 policy updates whose JSON embedded a deferred value, and 3 new ordering resources. Writing the criteria down first is what made the surprise legible; accounting for every element is what made the result trustworthy. Do not settle for totals that look close.
